# Прогресс обучения NestJS и PostgreSQL

Учебный проект — API интернет-магазина на NestJS с прямыми SQL-запросами через `pg`. Используем существующую локальную базу `learning` и схему `shop`. API каталога, авторизации и корзины готовы. Текущий этап — оформление заказа.

Фронтенд и его проверки ведёт ассистент. Реализация NestJS остаётся учебной практикой.

## Сделано

- [x] В PostgreSQL спроектированы и созданы восемь таблиц магазина. Фактическая схема `shop` подтверждена.
- [x] NestJS подключён к `learning` через общий `pg.Pool`. Настройки берутся из окружения, `start:dev` загружает локальный `.env`.
- [x] Проверены запрос при запуске и закрытие пула при остановке приложения через `app.close()` и `Ctrl+C`.
- [x] Работает `GET /products`. Контроллер, сервис каталога и сервис БД связаны через DI. Эндпоинт возвращает JSON-массив активных товаров с полями `id`, `name`, `price`, `stock`.
- [x] Работает `GET /products/:id`. Проверены JSON-объект товара, `400` для некорректного ID и `404` для отсутствующего товара. Параметр передаётся через `$1`, общий пайп проверяет положительные безопасные целые числа, а тип ответа описывает `id` и `price` как строки.
- [x] Работает `POST /products`. Через форму и временные таблицы PostgreSQL проверены `201` с созданным объектом и `400` для невалидного тела или отсутствующей категории. Неожиданная ошибка запроса возвращает `500`.
- [x] Работает `PATCH /products/:id`. На временных таблицах проверены частичное обновление, сохранение пропущенных полей, `stock: 0`, `description: null`, ответы `400` и `404`.
- [x] Работает `POST /auth/register`. На временной таблице PostgreSQL через HTTP проверены `201` с `id` и `email`, сохранение хеша Argon2id, `400` для невалидного email и несовпадающих паролей, `409` при конфликте индекса `user_active_email_idx` и `500` при конфликте первичного ключа. Два одновременных HTTP-запроса с одним email создали одну запись.
- [x] Работает `POST /auth/login`. На временных таблицах PostgreSQL через HTTP проверены `200` с `id` и `email`, `400` для невалидного тела и одинаковый `401` без создания сессии для неверного пароля, неизвестного email и неактивного аккаунта. Повторный вход выдаёт новый токен. В БД хранится хеш токена, сессия и cookie истекают через 24 часа, `Set-Cookie` содержит `HttpOnly` и включает `Secure` в production.
- [x] Работает `GET /auth/me`. Через HTTP на временных таблицах PostgreSQL проверены `200` с `id` и `email` для действующей сессии и `401` без cookie, с неизвестным токеном, для неактивного пользователя и при истечении сессии, в том числе ровно в `expires_at`.
- [x] Работает `POST /auth/logout`. Через HTTP на временных таблицах PostgreSQL проверены `204` с очисткой cookie при обычном и повторном выходе, в том числе без токена, `401` на `/auth/me` со старым токеном и `200` со второй действующей сессией пользователя.
- [x] Запись в каталог защищена `AdminGuard`. Через HTTP на временных таблицах PostgreSQL проверены `401` для гостя, `403` для покупателя и `201`/`200` для администратора на `POST /products` и `PATCH /products/:id`. Публичные `GET` каталога доступны гостям. `/auth/me` возвращает `id` и `email`. Смена роли на `customer` блокирует запись даже с действующей сессией.

## Дальше

1. **Корзина** — связи, `JOIN`, составные ключи, `UPSERT` и ограничения количества.
   - [x] Сверены связи по ER-диаграмме. `shop.users_carts.user_id` совпадает с ID владельца. В `shop.cart_items` составной ключ `(cart_id, product_id)` и проверка `products_count > 0` уже предусмотрены схемой.
   - [x] Записан контракт API. Все операции используют ID из действующей сессии через `UsersService.getCurrentUser`. Гость получает `401`. По обновлённому плану пустая корзина создаётся при регистрации.
   - [x] Работает `GET /cart`. Через HTTP на временных таблицах PostgreSQL проверены точные поля JSON, включая `productId` и `isActive`, строковые ID и цена, изоляция двух аккаунтов, отображение неактивного товара, `200 []` для пустой корзины и `401` без сессии, с неизвестным и просроченным токеном.
   - [x] `POST /auth/register` создаёт пользователя и пустую корзину одной командой с `WITH`. Через HTTP на временных таблицах PostgreSQL проверены `201` с `id` и `email`, сохранение хеша пароля, `409` для повторного email и полный откат при ошибке записи в `users_carts`.
   - [x] Недостающие корзины для существующих пользователей заполнены. Запрос к локальной базе `learning` подтвердил, что у пользователя `id = 5` есть корзина и у каждого пользователя есть строка в `shop.users_carts`.
   - [x] Работает `POST /cart/items/:productId`. Через HTTP на PostgreSQL подтверждены `200` при первом и повторном добавлении, строковый `productId` и итоговый `quantity`, ответы `400`, `401`, `404`, `409` и одна строка на товар. На двух соединениях второе добавление дождалось первого и получило `409`, в позиции осталось `2` при остатке `3`. Входной `productId` имеет тип `number`, как возвращает `PositiveIntPipe`.
   - [x] Работает `PATCH /cart/items/:productId`. Через HTTP на временных таблицах PostgreSQL проверены точное количество при увеличении, уменьшении и повторе, JSON ответа `200`, `400`, `401` и изоляция двух корзин. Отсутствующий или неактивный товар и отсутствующая позиция возвращают `404`, в том числе при запросе выше остатка. Существующая позиция при запросе выше остатка возвращает `409` и сохраняет количество.
   - [x] Работает `DELETE /cart/items/:productId`. Через HTTP на временных таблицах PostgreSQL подтверждены удаление активной и неактивной позиции, пустой `204` при обычном, повторном удалении и для отсутствующей позиции, `400` для некорректного ID, `401` без действующей сессии и сохранение позиций другого аккаунта.
2. **Оформление заказа** — транзакция, проверка остатков, блокировки строк, откат и конкурентные запросы.
   - [x] В локальной базе `learning` проверены существующие таблицы `shop.orders` и `shop.order_items`. Записан контракт для создания заказа, списка заказов и просмотра заказа.
   - [x] Работает `GET /orders`. Через HTTP на временных таблицах PostgreSQL проверены сортировка по `created_at DESC, id DESC`, строковые ID и суммы, дата ISO 8601 в JSON, `200 []`, `401` и изоляция аккаунтов. Тип `createdAt` внутри сервиса совпадает с результатом `pg` и равен `Date`.
   - [x] Работает `GET /orders/:orderId`. Через HTTP на временных таблицах PostgreSQL подтверждены `200` для владельца, сортировка `items` по ID позиции, сохранённые название и цена, пустой `items`, строковые ID и деньги, точность до максимального `bigint`, `400`, `401` и одинаковый `404` для чужого и отсутствующего заказа.
   - [ ] Реализовать `POST /orders` с телом `{ "address": "..." }`. В одной транзакции на одном клиенте взять позиции текущей корзины, проверить активность и списать остатки, сохранить заказ со статусом `pending` и позиции с ценами и названиями на момент оформления, рассчитать сумму в PostgreSQL и удалить оформленные позиции из корзины. Вернуть `201` с созданным заказом, `400` для некорректного адреса, `401` без сессии и `409` для пустой корзины, неактивного товара или нехватки остатка.
   - [ ] Проверить откат всего заказа при ошибке одной позиции и параллельное оформление. Две корзины с последними единицами товара должны дать один успешный заказ. Два одновременных запроса на оформление одной корзины должны создать один заказ.
